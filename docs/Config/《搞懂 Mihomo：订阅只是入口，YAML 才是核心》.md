对于使用 **Mihomo（Clash Meta）内核**的插件或客户端来说，无论配置来源是机场直接提供的订阅地址，还是通过订阅转换服务生成的订阅地址，本质上都是在解决同一个问题：**将远程的节点信息和配置内容转换成 Mihomo 内核能够识别和执行的配置结构。**

从原理上看，机场订阅地址本身并不是“配置文件”，它更像是一个**配置获取入口**。客户端通过 HTTP 请求访问订阅地址，服务器返回节点信息或配置内容；如果原始订阅格式不是 Mihomo 所需要的格式，就需要经过订阅转换服务，将节点信息转换成 Mihomo 支持的配置格式。

最终进入 Mihomo 内核后，核心需要处理的是一套结构化配置，例如：

- `proxies`：代理节点
- `proxy-groups`：策略组
- `proxy-providers`：远程节点提供器
- `rules`：分流规则
- `rule-providers`：规则集
- `dns`：DNS 配置
- `tun`：TUN 模式
- `geox-url`：Geo 数据库下载地址
- 以及其他 Mihomo 内核参数

而 **YAML 正是 Mihomo 配置最直接、最完整、最容易人工编辑的表达形式之一**。

因此整个关系可以理解为：

**机场订阅地址 → 获取节点/配置 →（必要时进行订阅转换）→ Mihomo 配置结构 → Mihomo 内核解析 → 执行代理、策略组、DNS、规则和分流。**

所以，订阅地址和 YAML 并不是同一个概念：

**订阅地址解决的是“配置从哪里来”；订阅转换解决的是“如何转换成目标格式”；YAML 解决的是“配置具体是什么”；Mihomo 内核负责的是“如何解析并执行这些配置”。**

这也是为什么直接使用 YAML 配置具有很高的可控性：不需要完全依赖订阅转换服务，可以直接对节点提供方式、策略组、健康检查、规则、DNS、Geo 数据库等进行精细调整。

简单来说：

**订阅是入口，转换是中间过程，YAML 是配置的具体表达，Mihomo 内核才是真正执行配置的核心。**
